# INTERVU — FINAL TEAM HANDOFF

## 1. Current Product
INTERVU is an adaptive technical assessment platform.

Core flow:
Candidate
→ technical question
→ answer
→ evaluator
→ CandidateKnowledgeState
→ adaptive strategy
→ next question
→ evidence collection
→ final report

The engine is NOT a static question generator. It adapts based on:
- correctness
- depth
- application
- uncertainty
- misconceptions
- contradictions
- demonstrated evidence
- competency state

## 2. Current Architecture

Frontend:
- Next.js
- candidate interview route (`/interview/[id]`)
- demo launcher (`/demo`)

- report/dossier (`/report/[id]`)

Backend:
- Next.js API
- InterviewOrchestrator
- CandidateKnowledgeState
- evaluator
- planner
- Groq provider
- Supabase persistence

LLM:
- Groq
- llama-3.3-70b-versatile
- GROQ_API_KEY
- no Gemini dependency

The adaptive state machine and behavioral harness are already implemented.

## 3. Important Routes

- `/interview/[id]`: Clean candidate experience.
- `/demo`: Judge scenario launcher.
- `/demo/[id]`: Judge Command Center containing candidate interview, intelligence panel, decision trace, competency map, uncertainty, expected evidence, adaptation timeline, and adaptation detected animation.
- `/report/[id]`: Final evidence-first assessment dossier.

Backend endpoints:
- `POST /api/interview`: Processes candidate answer, extracts evidence (Evaluator), plans the next strategy and generates the question (Planner), and returns it to the client. Uses in-memory deduplication to avoid duplicate requests hitting Groq.
- `POST /api/interviews/[id]/finalize`: Finalizes the assessment, determines final deterministic score, summarizes evidence via exactly ONE Groq call, and stores in the database.
- `GET /api/interviews/[id]/report`: Reads the persisted report directly from Supabase. NEVER calls Groq.
- `GET /api/candidates`: Returns list of canonical candidates.

## 4. Adaptive Strategies

The system uses the following strategies (from source code):
- BASELINE
- PROBE_DEPTH
- PROBE_REASONING
- PROBE_APPLICATION
- CLARIFY_CONCEPT
- TEST_TRANSFER
- TEST_EDGE_CASE
- CROSS_CHECK
- CHALLENGE_ASSUMPTION
- REMEDIATE
- MOVE_ON
- CONCLUDE

Strategy is selected based on candidate evidence. The planner is responsible for selecting the next strategy. The trajectory accurately represents the actual planner decision. The evaluator does NOT independently append fake strategy entries.

## 6. CURRENT KNOWN ISSUES

### Groq
- 429 rate limiting: Deduplication and exactly 1-retry backoffs are implemented, but severe API limits on the free tier may still result in `LLM_RATE_LIMITED` gracefully if limits are persistently hit.
- model availability: Hardcoded to `llama-3.3-70b-versatile`. 
- request deduplication: Fully implemented for concurrent React Strict Mode initializations and double-submits.

### Interview
- novelty detection: Saturated concept guards and semantic fingerprinting work, but might occasionally trigger 429s due to internal retries (max 3) if the LLM refuses to generate a novel question.
- initialization: Safe and idempotent via deduplication.

### Reports
- Reports are persisted correctly.
- GET `/report` invokes NO Groq calls (pure read).
- Finalization is idempotent (race conditions caught via `23505` unique constraint errors).
- The final report visual quality needs a design review.

### Database
- Session initialization uses standard Supabase UUIDs.
- RLS issues were observed locally on `assessment_reports` test runs, currently bypassed by disabling RLS or using Service Role Key. Make sure RLS is configured correctly for production.

### Frontend
- Rate limit UI implemented cleanly.
- Report page quality is decent but unpolished.

## 8. Demo Script

1. Open `/demo`
2. Select THEORY ≠ PRACTICE candidate scenario.
3. Start assessment
4. Give a strong conceptual answer ("A virtual environment is an isolated workspace for Python...")
5. Give a weak practical/application answer ("I don't know how to resolve dependency conflicts...")
6. Show: `PROBE_DEPTH` → `PROBE_APPLICATION` transition flash animation on the right panel.
7. Point to:
   - Why this question?
   - Expected evidence
   - Competency map
   - uncertainty drop
8. Complete assessment
9. Show final report (loading block)
10. Show evidence citations
11. Refresh report (F5)
12. Confirm report loads instantly and does NOT regenerate through Groq.

Misconception demo: Strong answer → deliberate misconception → REMEDIATE.
